## 3. 물리 아키텍처

> ⚠️ **본 아키텍처설계서는 학습용 가상 프로젝트(Helpdesk Lite) 기준이며 인프라·기술 스택 비종속 표기**. 사양·OS·DBMS·미들웨어는 모두 **권장 예시**이며, 실 프로젝트 적용 시 발주사 사내 인프라 표준 (예: 클라우드 vs 온프레미스, AWS vs Azure vs 사내 데이터센터, Linux 배포판 등)에 맞춰 확정 — 본 설계의 가치는 **이중화·백업·모니터링·확장 패턴**에 있음.

### 3.1 환경별 구성

| 환경 | 구성 | 용도 |
|---|---|---|
| 개발 | 개발 서버 1대 + DB 1 | 개발자 로컬 환경 + 통합 |
| 테스트 (스테이징) | App 1 + DB 1 + NAS 공유 | UAT·성능·보안 |
| 운영 | App 2 (이중화) + DB 1 (Master) + DB 1 (Standby) + NAS + LB | 가용 99.5% |

### 3.2 운영 환경 상세

```
[Internet (사내망)]
       │
       ▼
[L4 Load Balancer]
       │
   ┌───┴───┐
   ▼       ▼
[App 1]  [App 2]   ← Active-Active, Stateless
   │       │
   └───┬───┘
       │
   ┌───┴───┐
   ▼       ▼
[DB Master]──레플리케이션──>[DB Standby]
   │
   ▼
[NAS (사내 NFS)]

[배치 서버 1대] (SLA Notifier — Cron 1시간 주기)
[로그 서버 ELK] (App 로그 수집·검색)
[모니터링 Grafana] (메트릭 대시보드)
```

### 3.3 권장 사양 (운영)

| 노드 | CPU | RAM | Disk | OS |
|---|---|---|---|---|
| App 1·2 | 4 vCPU | 8GB | 100GB SSD | Ubuntu 22.04 LTS |
| DB Master·Standby | 8 vCPU | 16GB | 500GB SSD | Ubuntu 22.04 LTS |
| 배치 서버 | 2 vCPU | 4GB | 50GB SSD | Ubuntu 22.04 LTS |
| NAS | (사내 기존) | — | 1TB (확장) | NFS v4 |
| 로그 서버 (ELK) | 4 vCPU | 8GB | 200GB SSD | Ubuntu 22.04 LTS |

## 4. 가용성 설계 (NFR-INQ-002)

| 항목 | 설계 |
|---|---|
| **App 이중화** | Active-Active (LB 분배) — 1대 장애 시 다른 1대로 자동 |
| **DB 이중화** | Master-Standby (스트리밍 레플리케이션) — Master 장애 시 수동 페일오버 (RTO 1시간) |
| **백업** | DB 일 1회 풀 + 매시간 증분 / NAS 주 1회 / 백업 별도 스토리지 보관 |
| **복구 시험** | 분기 1회 — 백업 → 별도 환경 복구 → 정합 검증 |
| **MTTR 4h** | 알림 → 1차 대응 15분 → 원인 분석 1시간 → 복구 2시간 → 검증 45분 |

## 5. 운영성 설계 (NFR-INQ-004)

### 5.1 모니터링

| 영역 | 도구 | 핵심 지표 |
|---|---|---|
| App | APM (Datadog 또는 New Relic) | 응답시간 95%ile, 오류율, 처리량 |
| DB | DB 자체 + Grafana | 커넥션 수, 슬로우 쿼리, 디스크 사용율 |
| Infra | Grafana + Prometheus | CPU·RAM·Disk·Network |
| 비즈니스 | Grafana 대시보드 | 일일 접수·답변·SLA 미달율 |
| 로그 | ELK (Elastic·Logstash·Kibana) | App·Access·Audit 로그 |

### 5.2 알림

| 등급 | 트리거 | 채널 |
|---|---|---|
| Critical | 가용률 99% 미만, App 다운, DB 다운, 보안 침해 의심 | 즉시 SMS + 메일 + Slack |
| High | 응답 95%ile 2초 초과, 오류율 1% 초과, 디스크 80% 초과 | 메일 + Slack |
| Medium | SLA 미달율 일 1% 초과 | 일 1회 요약 메일 |
| Info | 배포 완료, 배치 정상 | Slack |

### 5.3 로그 정책

| 로그 종류 | 수집 | 보존 |
|---|---|---|
| App (요청·응답) | ELK | 3개월 |
| Access (Nginx) | ELK | 3개월 |
| Audit (인증·권한·취소·통계) | DB 별도 테이블 + ELK | 1년 |
| Slow Query | DB | 1개월 |
| 보안 이벤트 (403·권한 우회) | ELK + 별도 알림 | 1년 |

## 6. 확장성 설계 (NFR-INQ-005)

| 시나리오 | 대응 |
|---|---|
| 동시 사용자 2배 (400) | App 1대 추가 (수평 확장) |
| 동시 사용자 5배 (1,000) | App 3대 추가 + DB Read Replica 추가 (검색·통계 분리) |
| 데이터 증가 (5년 후 12만건) | 인덱스 효율 유지 — 파티셔닝 검토 (REG_DT 월별) |
| 모듈 부하 분리 | inquiry-search·inquiry-stats 별도 인스턴스 분리 가능 |

## 7. 보안 설계 (요약 — 상세는 보안설계서)

| 영역 | 설계 |
|---|---|
| 인증·세션 | JWT Access 30분 + Refresh 7일 (Auth Service) |
| 인가 (RBAC) | API Gateway 1차 + 컨트롤러 2차 + 서비스 3차 (본인 데이터 한정) |
| 전송 암호화 | TLS 1.2+ (Nginx 종단) |
| 저장 암호화 | DB 기본 + 비밀번호 BCrypt |
| WAF | Nginx + ModSecurity (또는 클라우드 WAF) |
| 입력 검증 | API Gateway + 컨트롤러 다층 |
| 마스킹 | 응답 미들웨어 (이메일·전화번호) |
| 감사 로그 | DB 별도 테이블 + ELK |

## 9. 배포 아키텍처

### 9.1 배포 절차

```
[개발자 PR] → [GitLab CI: 빌드·단위테스트·정적분석]
              → [통과 시 자동 머지 (develop)]
              → [수동 트리거 → 테스트 환경 배포]
              → [QA 통과 → 운영 배포 (Blue/Green)]
```

### 9.2 무중단 배포 (Blue/Green)

```
[현재 운영: Blue] (App1, App2)
       │
[새 버전 배포: Green] (App3, App4) ← 사전 부하 테스트
       │
[LB 트래픽 전환] (Blue → Green) ← 분당 10% → 50% → 100%
       │
[Blue 대기 30분] (롤백 대비)
       │
[Blue 정리] → 다음 배포 시 재사용
```
