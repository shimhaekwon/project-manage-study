### 1.2 사업 이해

A사는 메일·전화로 분산 처리되던 고객 문의를 통합하여 **누락 0건, 중복답변 0건, SLA 24h 준수**를 목표로 한다. 본 제안은 이를 4개월 내 구현·오픈하고 1년 운영 안정화까지 지원한다.

| # | 테마 | 차별 포인트 |
|---|---|---|
| 1 | **6하원칙 추적성** | 요구사항 ID부터 검수까지 RTM 한 줄 — 분쟁 0 보장 |
| 2 | **Mock-Impl Green 게이팅** | 설계 단계에 개발자 페르소나 롤플레이로 pingpong 사전 차단 |
| 3 | **변경관리 절차 사전 합의** | 무상 추가 과업 0 — 발주사·수행사 모두 보호 |

## 2. 사업관리 부문

### 2.1 추진 체계 (RACI)

| 역할 | 수행사 | 발주사 |
|---|---|---|
| **R** 실무 | PM 1·PL 1·분석/설계 2·개발 2·QA 1 | 정보화 1·현업(상담팀) 2 |
| **A** 책임 | 수행 임원 | 정보화팀장 |
| **C** 자문 | 솔루션 아키텍트, 보안 컨설턴트 | 외부 자문 (선택) |
| **I** 보고 | 본부장 | CIO |

### 2.2 일정 계획

```
2026-05  분석 (인터뷰·요구사항·RTM)            마일스톤 M1: 요구사항 승인
2026-06  설계 (DB·화면·API·아키텍처·보안)      마일스톤 M2: 설계 승인 (Mock-Impl Green)
2026-07~08(중) 개발·단위테스트                  마일스톤 M3: 코드 동결 (Freeze Day)
2026-08(말) 통합·UAT·성능·보안 시험            마일스톤 M4: UAT 인수
2026-09  컷오버·교육·검수·인수인계              마일스톤 M5: 검수 합격
2026-10~ 안정화 1개월 + 하자보수 12개월         (별도 운영 계약 검토)
```

### 2.3 품질관리

- **표준 고정**: 첫 주 표준(DB·API·에러·인증·실시간·날짜·금액) 동결, 산출물 작성 전 발주사 승인
- **리뷰 게이팅**: 단위테스트 95%+ / 코드리뷰 N명+ / 정적분석 Critical 0
- **Mock-Impl 롤플레이**: 설계 검수 시 1화면+1API+1테이블 의사코드 — 질문 0 = Green

### 2.4 위험관리

| 위험 | 영향 | 대응 |
|---|---|---|
| SMTP 외부 연계 지연 | SLA 알림 미동작 | 분석 단계 첫 주 인프라팀 합석, Mock SMTP 우선 |
| 발주사 UAT 사용자 가용성 | UAT 일정 압축 | 킥오프 시 사용자·일정 사전 합의 + 임원 백업 |
| 개인정보 마스킹 누락 | 법규 위반 | 06 보안설계서 단계 마스킹 정책 별도 검토 |

## 3. 기술 부문

### 3.1 시스템 아키텍처 (개요)

```
[FE: 모던 SPA (Vue3 또는 React)]
       ↓ HTTPS (JWT)
[API Gateway / RBAC]
       ↓
[BE: Spring Boot (또는 Node.js) — 모듈: inquiry-core / inquiry-search / inquiry-sla-notifier / inquiry-stats]
       ↓
[DB: PostgreSQL (또는 MySQL)] + [NAS: 첨부]
       ↓
[외부: 사내 SMTP] (이메일 알림)
```

> ⚠️ **본 산출물은 학습용 가상 프로젝트(Helpdesk Lite) 기준이라 기술 스택을 비종속적으로 표기**. 실 프로젝트 적용 시 발주사 표준·사내 IT 정책·사업 합의 결과로 확정 — 예: BE는 Java/Kotlin/Node.js 중 택1, FE는 Vue/React/Angular 중 택1 등.

### 3.2 적용 기술·표준

| 영역 | 적용 |
|---|---|
| 인증 | JWT Access 30분 + Refresh 7일, BCrypt |
| API | REST, JSON envelope (isSuccess/httpStatus/data/errors/timestamp) |
| 에러 코드 | UPPER_SNAKE_CASE (INVALID_PARAMETER 등), 숫자 접두사 금지 |
| DB | UPPER_SNAKE_CASE 컬럼, 공통컬럼 (REG/MOD/USE_YN/VERSION) |
| 보안 | TLS 1.2+, 마스킹 (이메일·전화), XSS·SQLi 방어, 첨부 화이트리스트 |

### 3.3 기능 요구사항 충족 매트릭스

| RFP ID | 요구사항 | 우선순위 | 충족 방안 |
|---|---|---|---|
| RFP-4.1.1 | 문의 등록 (제목·내용·카테고리·첨부) | M | inquiry-core / NAS 저장 / FR-INQ-001 |
| RFP-4.1.2 | 답변 작성 + 자동 알림 | M | inquiry-core + 비동기 SMTP / FR-INQ-002 |
| RFP-4.1.3 | 검색 (키워드·카테고리·상태·기간) | M | IX_INQUIRY_STATUS_SLA·IX_CATEGORY 인덱스 |
| RFP-4.2.3 | SLA 임박 자동 알림 | M | inquiry-sla-notifier 배치 (1시간 주기) |
| RFP-4.2.4 | SLA 통계 (일·주·월) | S | 사전 집계 테이블 + 당일 합산 |

### 3.4 비기능 요구사항 충족

| 항목 | 목표 | 충족 방안 |

## 4. 구현 방안

### 4.1 단계별 접근

| 단계 | 산출물 (대표) |
|---|---|
| 분석 (1개월) | 요구사항정의서 v1.0·RTM·인터뷰결과서 |
| 설계 (1개월) | DB설계서·화면설계서·API명세서·보안설계서·아키텍처설계서 |
| 개발 (1.5개월) | 소스코드·단위테스트결과서·형상관리계획서 |
| 테스트 (0.5개월) | 통합테스트시나리오·UAT결과서·성능/보안 시험성적서 |
| 인수 (포함) | 컷오버계획서·검수확인서·인수인계서·운영매뉴얼 |

### 4.2 산출물 검증

- 각 단계 종료 시 발주사 공식 승인
- RTM은 분석~검수까지 살아있는 문서로 유지
- Mock-Impl 롤플레이 Green 판정 (설계 단계)
