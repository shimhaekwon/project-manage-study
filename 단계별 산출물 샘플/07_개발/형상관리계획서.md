## 3. 브랜치 전략 (Trunk-Based + Feature Branch)

```
[main]      ← 운영 배포 가능 상태 (보호, 직접 푸시 금지)
   ▲
   │ Tag: v1.0.0, v1.0.1, ...
   │
[develop]   ← 통합 (테스트 환경 자동 배포)
   ▲
   │ MR (Merge Request, 1인 이상 승인 + CI 통과)
   │
[feature/HDL-NNN-짧은-설명]   ← 이슈 단위 브랜치
[fix/HDL-NNN-짧은-설명]       ← 결함 수정 브랜치
[hotfix/HDL-NNN-짧은-설명]    ← 운영 긴급 수정 (main 분기, main + develop 머지)
```

### 3.1 브랜치 명명

| 종류 | 형식 | 예 |
|---|---|---|
| 기능 | `feature/HDL-{이슈ID}-{설명}` | `feature/HDL-101-inquiry-cancel` |
| 수정 | `fix/HDL-{이슈ID}-{설명}` | `fix/HDL-DEF-007-sla-cron` |
| 긴급 | `hotfix/HDL-{이슈ID}-{설명}` | `hotfix/HDL-INC-005-db-pool` |
| 릴리스 (선택) | `release/v{major.minor}` | `release/v1.0` |

### 3.2 브랜치 보호

| 브랜치 | 보호 정책 |
|---|---|
| `main` | 직접 푸시 금지 / MR + 2인 승인 + CI 통과 / Force Push 금지 |
| `develop` | 직접 푸시 금지 / MR + 1인 승인 + CI 통과 |
| `feature/*`, `fix/*` | 자유 |

## 4. 커밋 메시지 규칙

```
[HDL-{이슈ID}] {type}: {요약}

{본문 (선택, 줄바꿈 후)}

{푸터 (선택, Closes/Refs)}
```

| Type | 의미 |
|---|---|
| feat | 신규 기능 |
| fix | 결함 수정 |
| refactor | 리팩토링 (동작 변경 없음) |
| test | 테스트 추가·수정 |
| docs | 문서 |
| chore | 빌드·설정 등 |
| perf | 성능 개선 |
| security | 보안 관련 |

**예시**:
```
[HDL-101] feat: 문의 취소 기능 추가 (FR-INQ-006)

- DELETE /api/inquiries/{id} 추가
- NEW 상태 + 본인 검증 + 낙관적 락
- SLA 알림 큐에서 해당 inquiry 제거

Closes HDL-101
```

## 5. 머지(Merge) 정책

### 5.1 MR (Merge Request) 절차

1. feature/fix 브랜치 → develop으로 MR 생성
2. CI 통과 확인 (단위테스트·정적분석·커버리지)
3. 코드리뷰 1인 이상 승인
4. Squash & Merge (커밋 깔끔히)
5. 자동 배포 (테스트 환경)

### 5.2 코드리뷰 체크리스트 (요약)

- [ ] 명명·들여쓰기·표준 준수
- [ ] 단위테스트 추가·실패 케이스 포함
- [ ] 권한 검증·본인 데이터 한정
- [ ] SQL Injection·XSS·CSRF 방어
- [ ] 시크릿 노출 없음
- [ ] 변경 로그 (CHANGELOG.md) 갱신 (필요 시)

## 6. 태그·릴리스 정책

### 6.1 Semantic Versioning

`v{major}.{minor}.{patch}`

| 변경 유형 | 증가 | 예 |
|---|---|---|
| 호환성 깨질 변경 | major | v1.x.x → v2.0.0 |
| 호환성 유지 + 신기능 | minor | v1.0.0 → v1.1.0 |
| 호환성 유지 + 결함 수정 | patch | v1.0.0 → v1.0.1 |

### 6.2 릴리스 노트

태그별 자동 생성 (커밋 메시지 + 이슈 링크) + 수기 보강.

```
## v1.0.0 (2026-09-11) — 운영 오픈
### Added
- 문의 등록·답변·취소·검색·SLA 알림·통계 (FR-INQ-001~006)
### Changed
- (해당 없음 — 최초 릴리스)
### Fixed
- (개발 단계 결함 종결 — 결함관리대장 참조)
### Security
- 마스킹·BCrypt·JWT·OWASP Top 10 대응
```

## 7. CI/CD 파이프라인

### 7.1 단계

```
[1. Lint·Format] → [2. Build] → [3. Unit Test] → [4. 정적분석 (SonarQube)]
       ↓
[5. 의존성 스캔 (npm audit·OWASP DC)]
       ↓
[6. Container Build] → [7. Container Push (Registry)]
       ↓ (develop 머지 시)
[8. Auto Deploy (Test Env)]
       ↓ (수동 트리거)
[9. Deploy (Staging Env)]
       ↓ (수동 트리거 + 임원 승인)
[10. Deploy (Production, Blue/Green)]
```

### 7.2 게이팅 (각 단계 PASS 필수)

| 단계 | 게이트 |
|---|---|
| Unit Test | 통과율 ≥ 95% |
| 정적분석 | Critical 0 |
| 커버리지 | 라인 ≥ 80%, 분기 ≥ 70% |
| 의존성 | Critical 0 |
