# 06. 설계

> **이 단계의 본질**: 분석 결과를 **개발자가 질문 없이 코드를 짤 수 있는 수준**으로 풀어낸다. 설계 단계의 모호함은 개발 단계 ping-pong과 직결된다. **DB·API·화면 표준은 첫 주에 고정**해야 후반 일괄 치환 작업이 발생하지 않는다.

## 3. 6하원칙 가이드

### Who (누가)

| 역할 | 수행사 측 | 발주사 측 |
|---|---|---|
| **R** 실무 | 아키텍트, UI/UX, DB설계, 시스템설계, PL | 정보화 검토자, 현업 화면 검토자 |
| **A** 책임 | PM | 발주 PM |
| **C** 자문 | 보안·인프라 컨설턴트, 감리 | 외부 자문, 감리 |
| **I** 보고 | 본부장 | CIO |

### When (언제)
- 분석 종료 직후 ~ 설계 종료 (4~10주)
- **첫 주: 표준 고정** (DB·API·UI·문서 표준) — 이후 변경 금지
- **마지막 1~2주: 검토·승인·구현 결정가능성 판정**

### What (무엇을)
- **수행사가 작성·제출**: 화면설계서, DB설계서, 인터페이스정의서, 아키텍처설계서, 보안설계서, 데이터이행계획서, 테스트계획서 초안
- **발주사가 제공·검토**: 표준(있는 경우), 검토 의견, 승인
- **공동 의사결정**: 표준 (양식·명명·코드체계), 화면 흐름, 권한·역할 매트릭스

### Where (어디서)
- 검토 회의: 발주사 회의실 (현업 검토는 대면 효과적)
- 작업: 수행사 작업실
- 산출물 보관: 합의된 협업 도구 + 형상관리

### Why (왜)
- **설계 표준 후행 등록 = 후반 일괄 치환** 폭탄 (참고: 축산물 플랫폼 4라운드 사례)
- **DB SSOT 경로 변경 = 다른 산출물 줄줄이 영향** — 한 번 정하면 끝까지
- **화면 검토 누락 = 개발 후 "이게 아니다"** → 재작업

### How (어떻게)
1. 첫 주 — **표준 고정** (DB 명명·API 응답 envelope·에러코드·UI 컴포넌트)
2. 아키텍처 설계 (논리·물리·배포·보안)
3. DB 설계 (ERD·테이블정의서·인덱스·시퀀스·공통코드)
4. 화면 설계 (사이트맵·스토리보드·컴포넌트)
5. 인터페이스 설계 (외부 시스템·내부 모듈 간)
6. 보안 설계 (인증·권한·암호화·감사)
7. 검토 미팅 (분야별, 양측 합석)
8. **구현 결정가능성(Implementability) 판정** — Mock-Impl 롤플레이
9. 설계서 v1.0 발주사 승인 → Baseline

### 5-2. 테이블정의서 표준 항목 (INQUIRY)

| # | 컬럼명 | 타입·길이 | NULL | 기본값 | 키 | 인덱스 | 설명 |
|---|---|---|---|---|---|---|---|
| 1 | INQUIRY_ID | BIGINT | N | (시퀀스) | PK | — | 문의 ID |
| 2 | TITLE | VARCHAR(200) | N | — | — | — | 제목 |
| 3 | CONTENT | TEXT | N | — | — | — | 내용 |
| 4 | STATUS | VARCHAR(20) | N | 'NEW' | — | IDX_STATUS_SLA | NEW/ANSWERED/CLOSED/CANCELLED (공통코드 INQ_STATUS) |
| 5 | CATEGORY_CD | VARCHAR(20) | N | — | FK→CATEGORY | IDX_CATEGORY | 카테고리 코드 |
| 6 | SLA_DUE_DT | TIMESTAMP | N | — | — | IDX_STATUS_SLA | SLA 만료 시각 (등록 + 24h) |
| 7 | REG_DT | TIMESTAMP | N | CURRENT_TIMESTAMP | — | — | 등록 일시 |
| 8 | REG_ID | VARCHAR(50) | N | — | FK→USER | — | 등록자 (GUEST) |
| 9 | MOD_DT | TIMESTAMP | Y | — | — | — | 수정 일시 |
| 10 | MOD_ID | VARCHAR(50) | Y | — | — | — | 수정자 |
| 11 | USE_YN | CHAR(1) | N | 'Y' | — | — | 사용여부 |
| 12 | VERSION | BIGINT | N | 0 | — | — | 낙관적 락 버전 |

복합 인덱스: `IX_STATUS_SLA (STATUS, SLA_DUE_DT)` — SLA 임박 알림 조회용 (FR-INQ-004)

> **관련 테이블**: ATTACHMENT (1:N, FK→INQUIRY.INQUIRY_ID, ON DELETE CASCADE) / ANSWER (1:N) / USER (N:1, REG_ID) / CATEGORY 코드 (N:1, CATEGORY_CD)

### 5-3. API 명세 표준 항목 (1 API)

| 항목 | 내용 |
|---|---|
| API ID | API-INQ-LIST-001 |
| 메서드·URL | GET /api/inquiries |
| 설명 | 문의 목록 조회 (상담사·관리자) |
| 인증 | JWT (Bearer) |
| 권한 | AGENT 이상 (GUEST는 본인 문의만 별도 API) |
| Query Param | status, categoryCd, keyword, page, size, sort |
| Validation | status ∈ {NEW, ANSWERED, CLOSED, CANCELLED}; size 1~100; page ≥ 0 |
| 응답 (성공) | `{ "isSuccess": true, "httpStatus": 200, "data": { "items": [...], "page": 0, "size": 20, "total": 137 }, "timestamp": "..." }` |
| 응답 (실패) | `errors[]`에 코드·메시지 |
| 에러코드 | INVALID_PARAMETER, UNAUTHORIZED, FORBIDDEN, INTERNAL_ERROR |
| 동시성 | GET이므로 자연 멱등 |
| 성능 SLA | 95%ile 0.5초, 100 TPS |

### 5-5. 상태머신 다이어그램 (문의)

```
[NEW] ──상담사 답변(FR-INQ-002)──> [ANSWERED] ──고객 확인 or 7일 경과──> [CLOSED]
   │                                  │
   │                                  └──고객 추가질문(7일 이내)──> [REOPENED] ──상담사 재답변──> [ANSWERED]
   │
   └──고객 취소──> [CANCELLED]
```

전이 조건·필수 검증·트리거·트랜잭션 경계를 각 화살표마다 명세. **REOPENED 시 SLA는 재기산하지 않음** (최초 접수 시점 기준 24시간 유지).
