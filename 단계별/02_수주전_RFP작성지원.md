# 02. 수주 전 — RFP 작성 지원

> **이 단계의 본질**: 발주사가 RFP를 작성할 때 **자문·검토 형태로 지원**한다. 직접 타이핑·공동 저자가 되면 **부정당 사유**로 입찰 자격이 박탈될 수 있다 (한국 공공·일부 민간). **선은 명확히, 도움은 실질적으로**.

---

## 1. 한눈에 보기

| 항목 | 내용 |
|---|---|
| 목적 | 발주사 RFP의 완성도를 높여 사업 성공률 향상 + 우리 도메인 이해도 강화 |
| 핵심 산출물 | RFP 검토의견서, RFP 자문 메모, (필요시) 평가기준 자문안 |
| 표준 소요 | 2~4주 |
| 투입 인력 | PreSales PM 1명 + 도메인 컨설턴트 1명 |
| 성공 신호 | RFP 발행 시 우리 의견이 반영 + 입찰 참여 자격 유지 |

## 2. 진입 조건 (Entry Criteria)

| 구분 | 항목 | 없으면? |
|---|---|---|

| ✅ 있어야 함 | 발주사 RFP 작성 담당자 (PM·정보화팀) | 발주사에 정식 자문 채널 요청 |
| ⚠️ 권장 | RFP 자문 범위·기간·대가 합의서 (간이) | 무상 자문이라도 범위 합의 메일은 필수 |
| ❓ 확인 | 발주처가 공공인지 민간인지 | 공공이면 **국가계약법·지방계약법** 적용 → 자문 형태 더 엄격히 제한 |

## 3. 6하원칙 가이드

### Who (누가)

| 역할 | 수행사 측 | 발주사 측 |
|---|---|---|
| **R** 실무 | PreSales PM, 컨설턴트 | RFP 작성 담당자(정보화팀) |
| **A** 책임 | 영업 임원 | 정보화팀장 / 발주 책임자 |
| **C** 자문 | 솔루션 아키텍트 | 현업 키맨, 법무·구매 |
| **I** 보고 | 본부장 | CIO |

### When (언제)
- 사업화 결정 ~ RFP 공고 직전
- **소요**: 2~4주. 4주 초과 시 발주사 일정에 부담.

### What (무엇을)
- **수행사가 작성**: RFP 검토의견서(서면 의견), 자문 메모(이메일), 평가기준 검토안
- **수행사가 절대 작성하지 않을 것**: RFP 본문 직접 타이핑, "최저가" 또는 "특정 솔루션명" 명시 요구, 평가배점 직접 결정
- **공동 의사결정**: 사업 범위, 일정, 기술 요구 수준, 평가 기준 윤곽

### Where (어디서)
- 화상회의 또는 발주사 사무실 자문 미팅
- 자문 의견은 **이메일·공식 문서** 로만 전달 (구두 자문은 증빙 부족)

### Why (왜)
- RFP 품질이 높아지면 → 본 사업 진행 매끄러움 → 차기 사업 신뢰
- 우리가 RFP를 미리 보면 → 03 제안 단계 준비 시간 확보
- **공정성 의식**: 우리만 유리한 RFP를 만들면 다른 입찰사가 부정당 신고 가능 → 사업 자체 무산

### How (어떻게)
1. RFP 자문 범위·기간·대가 합의 (간이 합의서·메일)
2. 발주사 RFP 초안 수령
3. **검토의견서** 작성 — 누락 항목·모호 표현·기술 타당성·일정 현실성 지적
4. 발주사와 검토 미팅 (1~2회)
5. 최종 의견 제출 후 **자문 종료 공식 통보**
6. 입찰 자격 검토: 자문 참여 사실이 **부정당 사유에 해당하는지** 법무 확인

## 5. 핵심 산출물 + 샘플

### 5-1. RFP 검토의견서 표준 양식

| 번호 | RFP 위치 (장·절·페이지) | 원문 발췌 | 의견 구분 | 의견 내용 | 근거 / 권고 |
|---|---|---|---|---|---|
| 1 | 3.2 / p.12 | "신속하게 처리되어야 한다" | 모호 | 정량 SLA 명시 필요 | "응답시간 1초 이내, 99.5% 가용성" 등 |
| 2 | 4.1 / p.18 | "최신 기술 스택" | 위험 | 부정당 사유 가능 | 기능·성능 요건으로 표현 권장 |
| 3 | 5.0 / p.25 | (누락) | 누락 | 비기능 요구사항 부재 | 보안·성능·확장성·운영 요건 추가 |
| 4 | 6.1 / p.30 | "6개월 내 완료" | 일정 | 비현실적 | 분석 1.5개월 + 설계 2개월 + 개발 4개월 + 테스트 1개월 = 8.5개월 권장 |

**의견 구분 코드**: 누락 / 모호 / 위험 / 일정 / 기술 / 법규 / 평가

### 5-2. RFP 표준 목차 (자문 시 발주사에게 권장)

```
1. 사업 개요 (배경·목적·범위·기대효과)
2. 사업 추진 일정 (전체 일정·마일스톤·검수일)
3. 사업 추진 체계 (조직·역할·의사소통)
4. 기능 요구사항 (FR-001~)
5. 비기능 요구사항 (성능·보안·가용성·확장성·운영성)
6. 시스템 요구사항 (인프라·OS·DBMS·미들웨어)
7. 데이터 요구사항 (이행·정합성·보존)
8. 인터페이스 요구사항 (외부 시스템 연계)
9. 보안 요구사항 (인증·암호화·감사·법규)
10. 품질 요구사항 (테스트·결함률·코드품질)
11. 산출물 요구사항 (단계별 제출·서식)
12. 교육·인수인계·하자보수
13. 제안 안내 (제출방법·평가기준·일정)
14. 계약 조건 (대가·검수·지급·분쟁)
부록: 현행 시스템 정보, 용어 정의, 양식
```

### 5-3. 평가기준 자문 (참고 비율)

| 평가 항목 | 권장 배점 | 비고 |
|---|---|---|
| 기술평가 | 80~90 | 사업관리·기술접근·구현방안·지원방안 |
| 가격평가 | 10~20 | 협상에 의한 계약은 가격 비중 낮음 |
| 우대 가점 | 0~5 | 인증(ISO·CMMI 등), 동종 실적 |

> ⚠️ 발주사가 우리에게만 유리한 가점(예: "특정 자격증 보유 인력 N명 이상")을 제안하면 **거절**한다. 입찰 무효 사유.

## 6. 리스크 & 흔한 실수

| 리스크 | 영향 | 대응 |
|---|---|---|
| RFP 본문을 직접 타이핑 | 입찰 자격 박탈 | 의견서 형태로만 제출, 발주사가 받아쓰기 형태 금지 |
| 우리 솔루션·제품명을 RFP에 명시 요청 | 부정당 신고 시 사업 무산 | 기능·성능 요건으로만 표현 |
| 평가배점 직접 결정 | 부정당 사유 | 권장안 제시 + 결정은 발주사 |
| 자문 종료 시점 모호 | 자문 명목으로 무료 노동 지속 | 종료일 명문화 + 종료 통보 메일 발송 |
| 자문 산출물을 03 제안서에 그대로 인용 | 정보 비대칭 시비 | 공개된 정보·우리 노하우만 사용 |
| 공공 사업에서 PMO·감리 자문 후 입찰 참여 | 이해상충 (법적 금지) | 자문 시점에 입찰 참여 의사 사전 공시 + 법무 검토 |

## 7. 종료 조건 (Exit Criteria)
