# 05. 분석

> **이 단계의 본질**: RFP 요구사항을 **구현 가능한 수준의 명세**로 풀어낸다. 모든 요구사항은 ID로 관리되고, **요구사항 추적표(RTM)** 가 분석~검수까지 살아있어야 한다. 여기서 누락된 비기능 요구는 09 검수 단계에서 폭탄으로 돌아온다.

| 성공 신호 | 발주사가 요구사항정의서 **공식 승인** + RTM Baseline 확정 |

## 3. 6하원칙 가이드

### Who (누가)

| 역할 | 수행사 측 | 발주사 측 |
|---|---|---|
| **R** 실무 | 분석가, PL | 현업 키맨, 정보화 담당 |
| **A** 책임 | PM | 발주 PM |
| **C** 자문 | 솔루션 아키텍트, 도메인 컨설턴트 | 외부 자문, 감리 |
| **I** 보고 | 본부장 | CIO, 사업본부장 |

### When (언제)
- 킥오프 직후 ~ 분석 단계 종료 (2~6주)
- **인터뷰 집중 기간**: 첫 1~2주
- **요구사항정의서 검토·승인**: 마지막 1주

### What (무엇을)
- **수행사가 작성·제출**: 인터뷰결과서, 요구사항정의서, RTM, As-Is 분석서, 분석 단계 종료보고서
- **발주사가 제공**: 인터뷰 대상자, 현행 시스템 자료, 법규·내규 자료, 요구사항 추가·확정 결정
- **공동 의사결정**: 요구사항 우선순위, 범위(In/Out) 경계, 비기능 목표값(SLA·성능·보안)

### Where (어디서)
- 인터뷰: 발주사 회의실 (현장감 중요), 화상 보조
- 작업: 수행사 작업실
- 산출물 보관: 합의된 협업 도구 (JIRA·Confluence 등)

### Why (왜)
- **요구사항 ID·RTM 부재 = 09 검수 시 통제 불가**. "이건 RFP에 있었다·없었다" 무한 분쟁.
- **비기능 요구 누락 = 오픈 직후 장애**. 성능·보안·운영성은 분석 단계에 못박아야 한다.
- 인터뷰 결과를 24시간 내 회신 받지 않으면 **기억 왜곡** 시작.

### How (어떻게)
1. 인터뷰 계획 수립 (대상·시간·질문지)
2. 인터뷰 실시 → 24시간 내 결과서 작성·발주사 확인
3. As-Is 분석 (조직·업무·시스템·데이터)
4. 요구사항 도출 → ID 부여 → RTM 등재
5. 요구사항정의서 초안 → 발주사 검토 미팅 (1~2회)
6. 비기능 요구사항 정량화 (성능·보안·가용성)
7. 발주사 **공식 승인** → Baseline 확정
8. 분석 단계 종료보고

## 5. 핵심 산출물 + 샘플

> 샘플은 모두 `샘플프로젝트_고객Q&A시스템.md` (Helpdesk Lite) 기준.

### 5-1. 요구사항정의서 표준 항목 (1건당)

| 항목 | 예시 |
|---|---|
| 요구사항 ID | FR-INQ-004 |
| 요구사항명 | SLA 임박 자동 이메일 알림 |
| 분류 | 기능 (FR) / 비기능 (NFR) / 데이터 (DR) / 인터페이스 (IR) / 보안 (SR) |
| RFP 출처 | RFP §4.2.3 / 제안서 §3.4.2 |
| 우선순위 | 필수 (M) / 중요 (S) / 권장 (C) |
| 요구 내용 | 문의 등록 후 SLA(24h) 임박 시점(마감 4시간 전)에 담당 상담사 이메일로 자동 알림 |
| 입력·출력 | 입력: inquiry_id / 출력: 발송결과(OK/NG, 사유코드) |
| 제약조건 | 동일 문의 중복 알림 1회만 / 이미 ANSWERED·CLOSED 상태는 발송 제외 |
| 가정·전제 | 사내 메일서버(SMTP) 정상 동작 / NTP 시계 동기화 (운영팀 책임) |
| 수용 기준 | 알림 정확도 100% (대상 누락·오발송 0), 임박 시점 ±5분 이내 발송 |
| 변경이력 | 2026-05-10 초안 / 2026-05-15 발주사 검토 반영 |

### 5-2. 요구사항 추적표(RTM) 표준 양식

| RFP ID | 요구사항 ID | 요구사항명 | 우선순위 | 설계 산출물 ID | 개발 모듈 | 단위테스트 ID | UAT 시나리오 ID | 검수 결과 |
|---|---|---|---|---|---|---|---|---|
| RFP-4.2.3 | FR-INQ-004 | SLA 임박 자동 이메일 알림 | M | DSN-INQ-006 | inquiry-sla-notifier | UT-INQ-009~012 | IT-INQ-SLA-007 | (미검수) |

> **RTM은 분석~검수까지 한 줄도 끊기지 않게 유지**한다. 끊기는 곳이 사고 발생 지점.

### 5-3. 비기능 요구사항(NFR) 정량화 체크리스트

| 분류 | 항목 | 정량 예시 |
|---|---|---|
| 성능 | 응답시간 (95%ile) | 화면 1초, API 0.5초 |
| 성능 | TPS (피크) | 100 TPS |
| 가용성 | 월간 가용률 | 99.5% |
| 가용성 | RTO·RPO | RTO 1시간, RPO 5분 |
| 보안 | 암호화 | 전송 TLS 1.2+, 저장 AES-256, 비밀번호 BCrypt |
| 보안 | 인증 | MFA 적용 범위, 세션 타임아웃 |
| 운영 | 로그 보존 | 90일 hot, 1년 cold |
| 확장 | 동시 사용자 | 1년 내 2배, 3년 내 5배 |
| 호환 | 브라우저 | Chrome·Edge·Safari 최신 2버전 |
| 이행 | 데이터 이행 | 정합률 99.99%, 차이 검증 보고 |

## 6. 리스크 & 흔한 실수

| 리스크 | 영향 | 대응 |
|---|---|---|

| 요구사항 ID 부여 누락 | 추적성 상실 → 분쟁 시 패배 | Baseline 확정 전 ID 일괄 점검 |
| 인터뷰 결과 회신 지연 | 기억 왜곡·재인터뷰 | 24시간 내 회신, 무응답 시 "확인 간주" 사전 합의 |
| 발주사 현업의 모호한 요구 ("알아서 잘") | 검수 시 "이건 그게 아니다" | 가정·전제 명문화 + 수용 기준 정량화 |
| Baseline 확정 후 무절차 변경 | 일정·범위 와해 | 변경관리 절차 발동 + 변경요청서 필수 |
| 법규·내규 요구 누락 (개인정보·전자금융 등) | 인증·감사 통과 실패 | 법무·컴플라이언스 별도 인터뷰 |
| 현업과 정보화의 입장 차 | 우선순위 충돌 | 양측 합석 회의 + 임원 결재로 우선순위 확정 |
